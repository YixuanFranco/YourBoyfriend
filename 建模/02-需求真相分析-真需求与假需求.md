# 建模 02 · 需求真相分析：真需求 vs 假需求

> 用途：回答重启项目的第一个问题——**用户在什么场景、什么痛点下需要这个"AI 伴侣"**。本文件是对两个《需求征集》Issue 全部 219 条评论（YB#2 105 条 + YG#1 114 条）的逐条判读，纠正"先做产品"的次序：需求真相在前，产品在后。
>
> 方法：场景还原 × 证据强度（复现频次 / reactions / 细节投入 / 跨库一致 / 作者认可）→ 真/假判别。

---

## 一、怎么判真/假：证据强度五档

| 信号 | 说明 | 例子 |
|:---|:---|:---|
| 复现频次 | 同一需求被 ≥2 人独立提出 | "脾气好"被 4+ 人次反复点名 |
| 社区加权 | reactions 高（+赞） | LGBT 需求单条 +32，全场最高 |
| 细节投入 | 用户愿意展开描述、给方案 | 暖床需求有人给出"电热毯+定时监测温度"完整实现方案 |
| 跨库一致 | 两边仓库都出现 | 会做饭、陪伴聊天两边都有 |
| 作者认可 | 项目方明确回应"有道理" | "思路一下子被打开了"（捏人 DIY） |

**假需求的三个特征**：一次性无场景（路过/围观/打卡）、反讽或玩梗（胸口碎大石）、字面无法产品化。

---

## 二、219 条评论的真相结构

| 类型 | 占比（估） | 含义 | 用途 |
|:---|:---|:---|:---|
| 真需求 | 约 35% | 可复现场景 + 真实痛点 + 行为倾向 | 定义产品本体 |
| 半真半假 | 约 15% | 欲望真实，表述是梗（性/亲密类居多） | 定义分级与边界 |
| 假需求（社区资产） | 约 50% | 观光团/打卡/玩梗/催更 | 不喂产品，喂传播与社区 |

> 关键：**假需求不是垃圾**。10 年攒下的"知乎观光团"和玩梗评论是这个项目最稀缺的资产——它们是流量、话题和社区基因。真需求喂产品，假需求喂传播，各司其职。

## 三、场景 × 痛点 × 真需求（核心表）

| # | 场景 | 痛点 | 用户原话证据 | 判别 | 需求本质 |
|:---|:---|:---|:---|:---|:---|
| 1 | 深夜独居 / 睡前 / 醒后 | 孤独，想有人说话、被叫醒 | "睡前小故事""早晨叫起床""能在一起聊聊天，谈谈心就好" | 真（高频+跨库） | **陪伴在场** |
| 2 | 情绪低落 / 委屈 / 被生活毒打 | 没人哄，缺情绪价值 | "脾气好""贴心的，要懂得哄人的""负责卖萌与鼓励" | 真（最高频性格词） | **情绪价值** |
| 3 | 加班 / 写代码 / 赶 ddl / 拖延 | 又累又缺人照顾，还缺"有用的人" | "程序员鼓励师：捶捶背捏捏腿讲笑话端茶送水""帮我改bug脾气要好""催我ddl""打dota带我躺赢" | 真（垂直人群，≥4 人次） | **有用性×关怀** |
| 4 | 生理期 / 生病 / 天冷 | 需要被照顾的证据 | "提醒月经周期""多喝热水""暖床（电热毯）" | 真 | **被照顾感** |
| 5 | 单身 / 空窗 / 被催婚 / 失恋 | 情感空缺、要归属感 | "给我个归宿""我有老婆了都还想有个铝朋友" | 真 | **关系身份 / 归属** |
| 6 | 节假日 / 纪念日 | 要仪式感、被记得 | "节日自动订花""每日甜言蜜语" | 真 | **仪式感** |
| 7 | 男用户想要男友（LGBT） | 现实不支持、需求被压抑 | "虽然我是一个男的，可是我也想要一个蓝盆友阿"（+32 全场最高赞） | 真（隐藏高需求） | **性别 / 性向自由** |
| 8 | 亲密 / 性需求 | 生理与情感要结合 | "会震动""会喘息会叫""sex 极其重要""每天早晨口醒" | 欲望真、表述是梗 | **亲密感（分级）** |
| 9 | 社交 / 炫耀 / 分享 | 要面子、群体认同 | "向哥们炫耀款""向前女友示威款""游戏对手款" | 半真 | **社交货币** |
| 10 | 创作 / 自定义欲 | 想亲手造一个 | "DIY女票""捏人""最好是个机器人，用代码表示属性" | 真（创造者需求） | **自定义** |

**隐藏的真需求（最高强度）**：被骂了 8 年的"要能跑的东西"——"整个项目现在只有 9 行 Py，你们在需求栏里 YY 得这么欢乐真的好么"。用户不是要更多需求，是要**一个真能用的东西**。这是全库最强的信号：不是功能需求，是**交付需求**。

## 四、假需求盘点（社区资产，不喂产品）

- 观光/打卡类："知乎观光团到此一游""路过""围观""加油努力啊"——约 50%，是流量资产。
- 玩梗类："会胸口碎大石""打麻将和扫雷基本技能""会震动"——梗是传播燃料；其中"会震动"背后的欲望是真的（见场景 8）。
- 反讽类："一行代码也没有？""找个男票有这么复杂吗""现在是不是真的烂尾了"——表面嘲讽，实为催更，指向"要能跑"。
- 社交应酬类："可以帮忙吗""求带"——招募信号，不是需求。

---

## 五、核心结论：产品本体不是"角色卡生成器"

把真需求收敛到最底层，用户的痛点是四个字：**被爱着的感觉**。

- 订饭、送花、提醒喝水，只是"有人记得我、在意我"的证据；
- 改 bug、带打游戏、催 ddl，是"你对我有用、你在参与我的生活"；
- 哄人、卖萌、脾气好，是"我的情绪被接住"；
- 暖床、会震动，是"这份关系有实体感"。

所以：**产品本体 = 一个能跑起来的最小 AI 伴侣（对话 + 记忆 + 关怀动作），角色卡/捏人只是它的"皮肤"和入口之一，不是产品本身。** 先做角色卡生成器等于先做皮肤再做身体，次序反了。

## 六、这对路线意味着什么（修正）

| 原计划（已暂停） | 修正后 |
|:---|:---|
| 先做 34 省角色卡生成器 MVP | 先做**需求验证**：一个 5 分钟可跑的"最小陪伴"（对话有性格、记得你、会主动关怀），看用户是否留下 |
| 以角色卡为产品内核 | 角色卡降级为功能模块，产品内核 = 关系体验（陪伴×情绪×有用×归属） |
| 用乙女/成人玩具倒推产品 | 它们仍是变现路径，但**先从场景 1/2/5（孤独、情绪、归属）验证真需求**，再谈变现 |
| README 主打"角色卡引擎" | README 主打"我们解决了什么问题、从哪 5 个场景开始"（需求真相前置） |

**一句话**：不是"造一个生成器让用户玩"，而是"造一个真的会疼你的东西，验证用户愿不愿意留下来"——留住了，再谈皮肤、谈变现、谈硬件。
