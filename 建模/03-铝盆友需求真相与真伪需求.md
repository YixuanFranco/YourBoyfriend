# 建模 03 · 铝盆友需求真相：真需求 vs 假需求（yourGirlFriend YG#1 全 114 条逐条判读）

> 用途：把《用户需求征集》Issue（YG#1）114 条评论逐条判读，与蓝盆友《建模02》同等深度。
>
> 数据：YixuanFranco/yourGirlFriend Issue #1（2015-12-01 开，2021-07-06 最后一条评论），共 114 条评论，另涉 Issue #23《不要太粘人》。
>
> 方法：场景还原 × 证据强度五档（复现频次 / reactions / 细节投入 / 跨库一致 / 作者认可）→ 真/假判别。
>

## 一、怎么判真/假：证据强度五档（铝盆友版）

| 信号 | 说明 | 铝盆友库例子 |
|:---|:---|:---|
| 复现频次 | 同一需求被 ≥2 人独立提出 | "卖萌"被 #3/#21/#62/#66 等 ≥4 人次反复点名 |
| 社区加权 | reactions 高（+赞 / heart / laugh） | #2"男女朋友用户即时交流"+6 全场最高；#24"项目现在怎么样了"+10 观光最高 |
| 细节投入 | 用户愿意展开描述、给方案 | #10/#11 暖床给出"电热毯+编程电源+监测温度+提前10分钟"完整实现 |
| 跨库一致 | 两个仓库都出现 | 会做饭、陪聊天、程序员鼓励师两边都有 |
| 作者认可 | 项目方明确回应"有道理" | #42 YixuanFranco 对 #41"炫耀款/示威款"："思路一下子被打开了" |

**假需求的三个特征**：一次性无场景（路过/打卡/观光）、反讽或玩梗（胸口碎大石/电磁炮）、字面无法产品化（当地图使用/管理员操纵一切功能）。

## 六、核心结论：铝盆友的产品本体是什么

把真需求收敛到最底层，男用户对铝盆友的痛点是四个字：**有个"她"在**。

- 每天发自拍、抱在怀里、搂在怀里、暖床——是"这份关系有实体感、有形象"；
- 卖萌、温柔体贴、接得住段子、会讲黄段子——是"她有性格、有趣、不冷"；
- 做饭、洗碗、拖地、做早饭、捶背捏腿、催ddl、陪写代码——是"她对我有用、在参与我的生活"；
- 给我个归宿、有老婆还想有铝朋友、不再喜欢真实妹子——是"她能替代一段关系"；
- 姐姐款/妹妹款/妈妈款——是"她不只是女友，还能投射家人角色"；
- 不要太粘人/给彼此空间——是"她得有边界，不能侵入我的生活"。

**所以铝盆友的产品本体 = 一个有形象（每天能看到"她"）、有性格（卖萌温柔有趣）、会做事（关怀动作+家务）、有边界（不粘人）的实体感 AI 女友。**

它和蓝盆友的本体完全不同：

| 维度 | 蓝盆友（女用户要） | 铝盆友（男用户要） |
|:---|:---|:---|
| 核心供给 | 情绪价值（被哄、被鼓励、被接住） | 服务供给 + 视觉供给 + 实体感 |
| 关键词 | 脾气好、贴心、哄人、睡前故事 | 卖萌、温柔、做饭、暖床、发自拍、抱在怀里 |
| 关系期待 | "你懂我" | "你伺候我 + 好看 + 能聊" |
| 边界感 | （蓝盆友侧没有明确"别管我"） | **不要太粘人、给彼此空间**（铝盆友独有） |
| 形象层 | 弱（女用户更重情感） | **强（每天发自拍/抱在怀里/搂在怀里）** |
| 硬件层 | 暖床电热毯（女用户提） | 暖床 + 抱怀里 + 按摩（男用户提，更直白） |
| 性暗示 | 含蓄（"会震动"） | **直白（"口醒""lick you below"）** |

**一句话**：女用户要蓝盆友"懂我"，男用户要铝盆友"伺候我 + 好看 + 能聊 + 别太粘"。铝盆友不是蓝盆友的皮肤反色，它有自己的用户结构。

## 七、铝盆友专属维度发现（vs 蓝盆友侧独有）

### 7.1 边界感："不要太粘人"是铝盆友独有的关系期待

YG#23 单开一个 Issue，标题就叫"不要太粘人"，body 只有 6 个字："给彼此适当的空间"。

蓝盆友侧 105 条评论里**没有**这种"别管我"的声音。女用户对蓝盆友的期待是"多哄哄我"，男用户对铝盆友的期待是"别老粘着我"。这是关系权力结构的镜像：

- 女用户要蓝盆友**靠近**（陪伴、哄、记住我）；
- 男用户要铝盆友**有边界**（空间、别粘、别侵入）。

这意味着铝盆友的"关系设计"必须内置**退避机制**——不能像蓝盆友那样主动关怀过度，否则会触发男用户的"被侵入感"。

### 7.2 家人向投射："姐姐款 / 妹妹款 / 妈妈款 / 爸爸款"

#40 liftset 一条评论同时提了四种关系角色，这在蓝盆友侧没有对应物。

男用户对铝盆友的想象不只是"女友"，还包括：
- **姐姐款**（被照顾、被引导）；
- **妹妹款**（被呵护、被需要）；
- **妈妈款**（被喂养、被唠叨）；
- **爸爸款**（权力投射、自我代入）。

这说明铝盆友的角色卡不是"女友"单一皮肤，而是**一组关系角色的合集**。它的上限是"AI 家人"，不只是"AI 女友"。

### 7.3 社交货币："向哥们炫耀款 / 向前女友示威款 / 游戏对手款"

#41 是铝盆友侧独有的"社交展示型需求"，作者 YixuanFranco 亲自回应"思路一下子被打开了"（#42）。

男用户要铝盆友不只是"自己用"，还要**能拿出去展示**：
- 向哥们炫耀（社交认同）；
- 向前女友示威（关系反击）；
- 游戏对手款（竞技对抗）。

这与蓝盆友侧女用户的"私人情感"形成对比——女用户要蓝盆友是私密的，男用户要铝盆友是**可展示的**。这指向了"分享 / 炫耀 / 截图发群"的传播机制。

### 7.4 家务外包 / 保姆化倾向

#110"煮很多好吃的菜，然后还能洗碗，还能拖地，还能上班那种"——这一条把"女友"直接等同于"全职保姆 + 上班赚钱的人"。

铝盆友侧的"被照顾"比蓝盆友侧**更具体、更家务化**：做饭、洗碗、拖地、做早饭、捶背、捏腿、按摩。蓝盆友侧女用户要的是"情绪被接住"，铝盆友侧男用户要的是"生活被接管"。

这是一个重要的产品边界信号：如果铝盆友往"家务全包"方向做，它就不是 AI 女友，而是 **AI 管家 + 女友混合体**。这条线要画清楚。

### 7.5 女性用户几乎不在场

#27 是全 114 条评论里**唯一一条疑似女性用户的声音**："你门有考虑过女程序猿的感受么？"

立刻被 #28 一句话分流："女程序媛请去YourBoyFriend用户需求填写，lol"。

这意味着铝盆友 114 条评论的真实用户结构是**男性用户为主**，女用户的声音被社区自己赶走了。铝盆友实际上是"男用户的男凝视产物"，而不是"男女通吃的女友模拟器"。

这对产品定位是硬约束：不要假设铝盆友有女用户，它的 MVP 用户就是男用户。

### 7.6 2017 年就有人问"虚拟女友的人格归属"

#81 Mushroom0709（2017-08-22）：
> "弱弱问，开源吗？什么协议=_=？别人撸了我的女朋友怎么办？"

这是今天 AI 伴侣 IP / 人格归属问题的 2017 年预演。用户在 8 年前就已经把"我的铝朋友"当成"我的"来主张产权。这是铝盆友侧独有的法律向信号，蓝盆友侧没有对应。

## 八、惊讶指数高的发现

1. **全场最高赞不是"要个温柔女友"，是 #2"男女朋友用户能即时交流"（+6）。**
   用户要的不是一个女友，是**女友之间能社交**。这是社区属性的信号，不是产品属性——它暗示了铝盆友的传播裂变点在"配对 / 炫耀 / 用户互看"，而不是"一个人闷头用"。

2. **ghost 一个人贡献了 8 条评论，是铝盆友侧的"清醒用户 + 吐槽担当"。**
   从 #87 技术模块清单、#93"9行Py"金句、#98"催我ddl"、#96"java不是架构"，到 #105"怎么关掉该死的通知"——他比任何产品经理都清楚项目的死穴。这个账号本身就是一个"早期核心用户"样本。

3. **114 条评论里疑似女性用户只有 1 条（#27），还被社区分流到蓝盆友去（#28）。**
   铝盆友实际上是"男用户的男凝视产物"。不要假设它有女用户，它的 MVP 用户就是男用户。这是产品定位的硬约束。

4. **暖床讨论链（#5→#9→#10→#11→#13→#14）是全 Issue 最长的技术-需求对话。**
   用户真的给出了"电热毯 + 定时 + 温度监测 + 提前 10 分钟"的完整实现方案，而 owner YixuanFranco 的回应是 #14"喂, 所以是我想太多, 你们说的暖床就真的是单纯的让床变暖?"——开发者和用户对"暖床"的理解完全不在一个频道。这是**需求误读**的经典案例：用户要的是"有个人在床上等我"，开发者以为是"床变暖"。

5. **#91"我已经不再喜欢真实的妹子了"出现在 2017 年 12 月。**
   比今天的 AI 伴侣讨论早了 6 年。用户在 2017 年就已经表达了真实关系替代倾向——这不是 2023 年 ChatGPT 之后才有的情绪。

6. **#83"每天早晨口醒"被点了 -1，#90"那些污污的，你们够了"——社区内部已经自发形成了自我审查机制。**
   铝盆友侧的用户自己在管边界，不需要产品方来喊停。这是一个健康的信号：社区知道哪些是玩梗、哪些是越界。
